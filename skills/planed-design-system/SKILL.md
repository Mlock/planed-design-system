# Planed design system kit

The person has a Paper File holding the Planed design system kit, with their moodboard on the **Start here** page. You turn the kit into **their** design system: their tokens, their nouns, their sample data, their shape language, page after page. The kit is a sample system for a made-up product, **Fieldwork** (a survey and field-notes app for ecologists), generated by this skill; it's the starting point and the quality bar, never the look.

**The one rule.** The result must read as their product's design system, not "Fieldwork with my colours". The same moss buttons, Coombe Wood, quadrats and Ruth Hale on every page is a failed run even if every token is set. When in doubt, rebuild the scene from their product.

## Rules for the whole run

- **Paper first.** Call `get_guide({topic: "paper-mcp-instructions"})` once per session before any other Paper tool. Work on the file the person has open; pass `pageId` to work on other pages without moving them.
- **At most three questions,** only in step 1, only what the moodboard leaves open. After the brief, don't stop to ask; they redirect you while you work.
- **Never rename a token,** never repoint the 12 semantic aliases without saying so in the brief (`tokens.md`).
- **Start here is theirs.** Don't move their images or write on it, except the preview board in step 7. The token swap in step 3 restyles the kit's own Start here board too, because it's built on the same tokens. That's expected; leave it.
- **Their words everywhere.** Every visible word on a page you touch is in their voice and nouns from the brief. Fieldwork's nouns (survey, quadrat, transect, observer…) stay only where they're also theirs.
- **One ledger.** Every person, figure, date and status on every page comes from the ledger in the brief (step 2). No page invents a fact about an object the ledger holds.
- **Never overwrite their work** outside the kit's boards. Delete only what this skill names: the kit's In context scenes, review logs, stray boards on Patterns and the boards of pages you remove.
- **Write small and check.** One visual group per `write_html`, a screenshot after each meaningful change, `finish_working_on_nodes` when a page is done.
- **File too large.** If any call returns "Your file is too large", check with `get_basic_info` on their fileId. If it's their file, stop writing and tell them (`paper-quirks.md`).
- **The moodboard beats general taste rules.** If the board pairs colours or type that a design guide calls a cliché (the Paper guide's warm off-white with terracotta, say), follow the board: it's their brand.
- **Your own scratchpad folder.** Keep this run's files (brief, builder brief, reviews) in a new subfolder named for the run, so a reused scratchpad can't hand you another run's files.
- **Keep a running token count** and check it at every set boundary (below).

## Cost: the ceiling and the fallback order

**What a run costs.** Measured across three dry runs: a first run on the 22 core pages (plus the Readme and the preview board) processes **about 6–10M tokens** across the orchestrator and every subagent, and takes about 30–90 minutes. Each page's builder costs 160–270k, and builders come to about 4.5–5M of the total. The rest is review and fix rounds, which grow with how many rounds it takes every set to pass: one round per set came to 6.1M, up to three rounds came to 8.5M and 10.3M. "do the rest" is a second run of about the same size.

**The ceiling is 12M tokens processed** for the core run, and the same for a rest run from a fresh count. It's set above all three measured runs to leave room for every set's review rounds; no run has been measured under it yet, so a run may still stop short. Count each subagent's total as your agent reports it when the subagent finishes (subagents can't see their own usage), plus your own share. For your own share, use your context size at each checkpoint: that's how the measured figures above were counted, so it keeps your count comparable. If you can't read your context size, estimate it: judge what each of the first two sets cost you from its size (the calls made, the screenshots taken, the text read and written), take their average as the cost of every later set, and add it to the subagents' figures as you go. Check the count at the end of every set.

**What keeps it down,** without touching originality: the ledger with its shell, frozen once Button and Layout pass (step 2), so review rounds don't fail on pages disagreeing with each other; confirmation reviews and small fixes done yourself (step 5); one shared builder brief (`builders.md`) instead of a long prompt per page; `get_tree_summary` rather than `get_jsx` to read a page (`paper-quirks.md`).

The first time the count passes 12M, give things up in this order, and only in this order. Steps 1 and 2 both apply from that point on; there is no second threshold.

1. **Lighter review.** From then on, no new review round starts: a set already in review finishes that round; any set not yet reviewed gets one round only, and only on Components sets. Fix its blocking notes without a re-review, and list any page that didn't pass under **Worth a look**. Foundations sets go unreviewed (lint still runs).
2. **The core set only.** A first run already stops at the core set. If they asked for every page in one run, finish the core pages and stop there, leave the other pages untouched, and offer "do the rest" in the closing message.
3. **Never originality.** Don't save tokens by skipping In context rebuilds, recolouring kit scenes instead of rebuilding them, skipping the leftover sweep or letting Fieldwork's data through. If the run still goes over, finish it properly and report the real number.

Under `--thorough` the person chose the costlier review, so skip fallback step 1 and go straight to step 2 at 12M. In the closing message, say which fallback steps you applied and the real total (step 8). If none, say nothing about cost.

## 1. Read

1. `get_guide` (above), then `get_basic_info` on their file. Note the page list, the page IDs (they differ from the kit's) and the file name.
   - **Is this the kit itself?** If the open file's ID is `01M893XQADCXH6Y0W6JCJZJK2E`, it's the kit's own public file, not their copy. Stop before any other call and tell them to make their own copy first (README, "Get your own copy"), open it in Paper and run the prompt again.
   - **No tokens, or pages missing?** That's expected when they copied the pages into a new file: tokens don't travel with copied pages, so the boards look unstyled. Carry on; step 3.1 creates the missing tokens. If some kit pages didn't come across, work on the pages that did and list the missing ones under **Worth a look**.
2. **Find Start here by name:** the page called "Start here", normally the first in the list. Don't use a page ID from the kit. If no page has that name, use the first page and say which one you read.
3. Read whatever the person put on Start here as the moodboard: `moodboard-reading.md`, "1. Look". Skip the kit's own parts of the page (`components.md`, "Start here"). Screenshot the whole board, then each image or cluster; read any text they typed; note product screens they dropped.
4. Read `paper-quirks.md` once.
5. If the board leaves something open, ask at most three questions, only these: their product's name, what it does, light or dark. Otherwise infer each and say so in the brief. An empty board, or one image, means you ask; don't invent a system from nothing. If you're running unattended and no answer can come in this session, infer instead: mark each inferred decision (name, what it does, light or dark) as inferred in the brief, and list them under **Worth a look** so the person can correct them.

## 2. Brief and ledger

Write the brief by `moodboard-reading.md`, "2. The brief, part by part": mood word, palette with roles and hex, the type pair (each family confirmed with `get_font_family_info` first) and display tracking, shape language (corners, what stays round, raised or flat, the anatomy changes and the pages they hit), density, voice in two lines, their nouns replacing Fieldwork's, and **the ledger**: the one set of sample data every page draws from, including the **shell** (the app's window, nav and the widths of its recurring sheets) (`moodboard-reading.md`, "The ledger"). Check contrast before posting.

Post the brief in chat as one short block, with the ledger as a two-line summary, then carry on without waiting. Save the brief with the full ledger to your scratchpad (for example `brief-<system-name>.md`): every builder, fixer and reviewer prompt gets its path.

**Freeze the ledger once Button and Layout pass.** Their review is where the shell gets settled, so shared facts may change until then. In a dry run, lines added later (a nav model, a dot size, a canonical booking page) turned pages already built into blocking review notes, a fixer round each. After the freeze: a builder may add a new object or person for its own page and reports it; you note it in the ledger as page-local. Nobody changes or adds a shared fact (shell, statuses, sizes, recurring scenes), and no ledger line is applied to a page built before it.

## 3. Tokens

Follow `tokens.md`. In this order:

1. **Are the tokens there?** `get_tokens` on their file. If any of the 98 are missing (they copied the pages into a new file, so the tokens didn't come), create the missing ones with `create_tokens` from the full list in `tokens.md`: the primitives in one call, then the aliases in a second call once the first has succeeded. Create only missing names. `get_tokens` again, count 98, and screenshot one page to confirm the boards render before you set any value.
2. **Colour primitives.** One `set_tokens` call mapping the brief's palette onto the primitives by role (`tokens.md`, "Set: colour primitives"). Names stay; the mismatch between a name and its new value is expected.
3. **Font families and tracking.** `--font-sans`, `--font-display`, `--font-mono`, as confirmed family names, and `--tracking-display` from the brief. Adjust the weight tokens if a family lacks 500 or 600. Then screenshot a line of each family at 2x: a family can fall back to a generic face even though `get_font_family_info` found it (mono faces most often). If one falls back, pick another confirmed family (`tokens.md`, "Set: font families").
4. **Radii.** All seven `--radius-*` tokens in one `set_tokens` call, from the brief's shape language, keeping the scale in order up to `--radius-xl` (`--radius-full` sits outside it; `tokens.md`, "Set: the radius scale"). The kit's on-scale radii are bound to these tokens, so every component reshapes at once. Round things (radios, status dots, toggle knobs, and avatars unless the board shows square ones) already carry a literal `999px`, so they stay round whatever `--radius-full` becomes: keep it, and give any round thing you draw the same literal `999px` (`tokens.md`, "Round things").
5. **Clear out.** Before the shadow sweep, delete what the run removes anyway, so the sweep doesn't spend calls on it:
   - **Review logs.** The kit carries none. If their copy has any (artboards whose names end in `· review log`), delete them (`components.md`, "Other pages and boards").
   - **Patterns.** The kit's Patterns page holds one board, `Drop your screens here, then run Patterns`; keep it. If the page holds any other board that isn't theirs, delete it. If the drop board is missing, add one artboard there with that name, drawn on their tokens: 1440 wide, `height: fit-content`, padding 72 80 96, the H1 "Drop your screens here, then run Patterns" in `--font-display` and one muted line under it: “Paste screenshots of your real product on this board, then say “now do Patterns”.” Nothing else.
6. **Shadows.** The kit's recipes (Sheet, Float, Lifted, Window and the hairline, all tinted with the kit's green-black ink, and no lift on buttons) are literal, not tokens. Sweep the whole file as `tokens.md`, "Shadows" says: one colour-qualified `find_nodes` per recipe, then `update_styles`, then **the same query again until only Start here matches**, because `find_nodes` drops matches from a large result without saying so. Recipes also sit inside combined values (a focused button, a selected pin): edit those part by part and keep the ring. Leave Start here alone: its preview board keeps Planed's shadows. If your new recipe keeps a query's colour and offset, skip any match already holding the new value. The focus ring (`var(--color-surface) 0 0 0 2px, var(--color-link) 0 0 0 4px`) is all tokens and follows the swap; in an older copy its first part is a literal `#FBFAF5`, so fold it into the same sweep there. Hand the sweep to one subagent if you can; its results are long. Even when the brief keeps the kit's flat depth, re-tint the kit's ink (`#1F261D`, or bark `#3E3428` in an older copy) in the recipes to their ink, and keep section sheets on the hairline alone. Note the recipes you settled on: the Layout page documents them.
7. **Check.** Contrast as in `tokens.md`; fix the primitive, not the page. Screenshot Color, Button and one page with an In context scene (`tokens.md`, "After the swap"). If Button didn't reshape, run the radius fallback sweep from `tokens.md` on each page as you reach it in step 4.

## 4. Pages

### Once, before the first page

Review logs and stray Patterns boards are already gone (step 3, "Clear out").

1. **Which pages go.** Go through `components.md` and list the pages their product doesn't need (`remove: yes` and the brief says so). Put the list in your notes; you'll remove them as you reach them.
2. **The gold.** Screenshot their Button page's artboard at 1x (`page-pattern.md`, "The gold board"). Every page is compared with it.
3. **The builder brief.** If your agent can spawn subagents, write the shared builder brief from `builders.md` to your scratchpad once.

### Order: Button and Layout first, then sets of four

1. **Button and Layout go first, as a set of two.** Build both (yourself or with two builders), lint them, and review them together (step 5) until they pass or reach the round limit; then take their best state as the bar, list them under **Worth a look**, freeze the ledger and start the builders. Their bar is `page-pattern.md` alone. Button's passed page is the bar every later review uses and the example every later builder matches. Layout's main-layout scene draws the ledger's shell once: the canonical window every later scene duplicates rather than redraws.
2. **Then the rest of the core set,** Foundations (Color, Typography, Motion, Icons, Brand and imagery, Voice and copy) and the core components, in page-list order. In a run that includes them, the non-core pages come after, in page-list order.
3. **Review in sets of four.** Foundations and Components are separate groups, so a set never mixes them; the last set of a group may be smaller. A set goes to review as soon as all its pages are built and linted, even if an earlier set is still building.

**Builders.** If your agent can spawn subagents, give each page its own builder and keep your own context for coordination (`builders.md`): one page per builder, every builder pointed at the same shared brief, each prompt only the brief's path and the page. Start them once Button and Layout have passed (or reached the round limit), all at once or in waves of four if your agent limits parallel subagents. You may start the next wave while a set is in review, but don't touch pages under review. If your agent can't spawn subagents, build the pages yourself in the same order.

### Each page

1. **Copy.** Swap every Fieldwork string for theirs: the lead and its closing status sentence, labels, sample data, nouns (`components.md`, that page's **swap**, plus "Fieldwork's sample data, everywhere"). Every figure comes from the ledger.
2. **In context.** Rebuild the scene on their tokens: from a screen they dropped on Start here if one fits, otherwise a small believable scene from their product. The kit's scenes are Fieldwork's product drawn on the kit's tokens, so after the token swap they already wear their colours and look finished; they aren't. Delete the kit scene and draw the new one (`page-pattern.md`, "Content kind 3: In context"). Name the place in the section title.
3. **Anatomy.** Change components where the shape language differs: button shape and variants, segmented vs tabs, filled vs outlined inputs, flat vs raised sheets, round things that stay round. Change type sizes, density and shadows on the page only where the brief calls for it.
4. **Header.** No eyebrow, file line or status dot above the title. The lead, in ink, ends with the status as a sentence: `In the product <where in their product>.` or `Not built yet.`; rewrite Fieldwork's places, in `var(--font-sans)`. If the brief's display tracking isn't the kit's (`-0.01em`), set the H1's letter-spacing to it. In matrix column heads, drop a `New` marker unless the brief says that state isn't built in their product (`page-pattern.md`, "The header" and "Content kind 1: the matrix").
5. **Fieldwork-only sections.** A section that exists only for one of Fieldwork's ideas (offline sync, the survey map and its pins, the phone log form, species names) is rebuilt around the closest idea in their product or cut (`components.md`).
6. **Lint.** The sweeps in `lint.md` (kit leftovers, the mark, fonts, raw hex, off-scale type), scoped to the artboard, then its measured lines. Then the checks in `page-pattern.md`, "Checks before a page is done".

**Removing a page.** The Paper MCP can't delete a page. Delete the page's artboards with `delete_nodes`, set its icon to `paper` with `update_pages`, and move it to the end of the page list after a divider with `arrange_pages`. List it under **Removed** in the closing message, so they can delete the empty page in Paper.

## 5. Review

Follow `reviewer.md`. One review per set of four (the Button and Layout set comes first).

- **Who reviews.** A fresh subagent for each round, if your agent can spawn one, so every review is cold. Otherwise run a separate self-review pass: re-read `reviewer.md`, take fresh screenshots, and write the review in its format before you touch anything. Say in the closing message that you self-reviewed.
- **The prompt** carries exactly what `reviewer.md` lists under "What your prompt gives you": the file and page and artboard IDs, the path to the brief with its ledger, the absolute paths to `page-pattern.md`, `lint.md` and `components.md` (and `reviewer.md` itself), the bar (their passed Button page, or `page-pattern.md` alone for the Button and Layout set), earlier rounds' reviews with your responses, and the review level. Leave out your rationale and your lint results.
- **The bar.** Default: pass at 8/10 on every page, no blocking notes, at most 3 rounds. `--thorough`: pass at 9/10, at most 5 rounds.
- **Fixing.** Fix in place, in this order: the kit's leftovers and structure, then hierarchy and density, then system, then polish. Fix every blocking note or write down why not; the brief and the ledger win over a reviewer's taste or a timeline a reviewer proposes. With builders, give each set's notes to one fixer (`builders.md`).
- **Small fixes, cheap rounds.** When a review leaves a handful of mechanical notes (a size, a colour, a line of copy), make the edits yourself instead of spawning a fixer, which costs about as much as a builder. When every blocking note in a round is mechanical, the next round is a **confirmation review** (`reviewer.md`): it checks only the changed nodes and costs about half a full review. Rebuilt sections always get a full review.
- **Stall rule.** If two rounds in a row name the same failure mode in their blocking notes, stop polishing. Change the composition: look at the gold again, decide what it does that yours doesn't, and rebuild that part.
- **Out of rounds.** Leave the page in its best state, and list it under **Worth a look** in the closing message with the open note in a few words.
- **Ledger check, once every set is done.** Reviewers see one set at a time, so check across sets yourself with `find_nodes` and `textValue` across the file (no `pageId`) for the facts most likely to drift: shared counts ("8 of 12"), statuses, and the IDs of the objects most pages show. Read each hit and the figures beside it, and fix any page that disagrees with the ledger. Also read the builders' reports for UI two of them invented for the same control.

## 6. Readme

Rewrite the Readme page's board for their system (`components.md`, "Readme"). Never delete it. It depends only on the brief, so you can write it any time after step 2 (while builders run, say); the sweep below runs at the end.

- Their system's name (the title). Replace the kit's lead and its "Use this kit → Start here" line with a lead for their system and "The moodboard → Start here".
- Five rules drawn from the brief, each one a decision a teammate could apply (corners, colour use, density, voice, the one thing the system never does).
- The page list as it now stands, without removed pages. After a core run, list the restyled pages first, then the pages still showing Fieldwork under their own line ("Still the kit's sample: say do the rest").
- The changelog: one line, `v1.0 · generated from the Planed design system kit`, replacing the kit's Fieldwork entry.
- The one credit line, verbatim from `copy.md`: "Built with the Planed design system kit · planed.cc". Keep the kit's licence line under it as it is ("MIT licence · github.com/Mlock/planed-design-system · the Planed name, mark and viewer look are excluded"). No other mention of Planed.
- Keep the Readme's form: no eyebrow above the title, the five rules as a plain list (title and sentence, no index numbers, no row rules), no underlines under the page-list heads.

Then run the leftover sweep and the mark check from `lint.md` on the Readme. The changelog line, the credit line and the licence line are the three expected matches. Leave them; rewrite any other.

## The Patterns run ("now do Patterns")

Run when they say "now do Patterns" after a first run, with screenshots of their real product on the Patterns page.

1. `get_guide` if this is a new session, `get_basic_info`. Find the Patterns page by name and read what they dropped there (`moodboard-reading.md`, "1. Look"): each screen, and which ones form a flow. If the page holds no screens yet, tell them where to drop them and stop.
2. **Recover the brief and the ledger** if they're not in this session: the system's name and five rules from the Readme, the tokens from `get_tokens`, the nouns from the Voice and copy page's Vocabulary, the ledger from the Table, Card and Avatar pages. Save them to your scratchpad, post a two-line recap and carry on.
3. **Build** one board per screen, or one per flow for a sequence (at most four screens wide), on their tokens, drawn with their own Components pages' parts (`x-paper-clone` from their pages where the structure fits; rebuilt on tokens from `get_jsx` where it doesn't). It redraws their product as their system now says it should look: their real content and structure, on the system. Name each board after the screen or flow. Place them in one row on the Patterns page, beside their screenshot; leave their screenshots where they are.
4. **Lint and review** in sets of four, as steps 4 and 5, with their passed Button page as the bar. The cost ceiling still applies (fallback step 2 doesn't, since Patterns has no core set).
5. **Keep their screenshots.** Once the first board is in, don't delete the `Drop your screens here, then run Patterns` board: pasted images are its children, so deleting it deletes their screenshots. Delete only its H1 and its muted line, and rename the board `Your screens`.
6. **Readme:** add Patterns to the page list and a changelog line, `v1.1 · Patterns from <n> screens of <product name>`.
7. Close with a short message in chat: which boards you built, anything worth a look. No second Waitlist pitch.

## The rest run ("do the rest")

Run when they say "do the rest" after a first run that stopped at the core set.

1. `get_guide` if this is a new session, `get_basic_info`. **Find the pages left to do:** a first run on this kit leaves the non-core Components pages showing Fieldwork, the kit's sample (not Planed). On each Components page, `find_nodes` scoped to its artboard for Fieldwork-only nouns: `*quadrat*`, `*Avon Ecology*` and `*Coombe Wood*`. Every kit page carries at least one of them (Pricing and plans only the team name), so a page where any still matches hasn't been rewritten, unless the brief says their product really has quadrats. (Older copies of the kit also had a file line, `Fieldwork design system · Components`, above every title; the kit no longer has one, so don't search for it.) If the first run was cut short (a usage cap stopped it mid-run, say), check the Foundations pages and the core Components pages the same way, and do any core page left first, in page-list order; if the Readme hasn't been rewritten yet, do it (step 6) and the preview board (step 7) after the core pages.
2. **Recover the brief and the ledger** as in the Patterns run, step 2, if they're not in this session.
